# HWIDMaster-0902.exe 静态解剖报告

- 样本：`HWIDMaster-0902.exe`
- 大小：45,244,416 字节（0x2B26000）
- MD5：`6e52de4aeb2a760d5453e354e18bac41`
- 类型：PE32（Intel 80386，GUI 子系统），ImageBase `0x400000`，无重定位、无调试目录、无 TLS
- 复现命令：`python3 tools/pe_triage.py samples/HWIDMaster-0902.exe --json results/triage.json`

---

## 1. 一句话结论

**这个文件不是"加了壳的程序"，而是"一整块加密载荷 + 一个空 PE 头"。**
磁盘上不存在任何可执行字节：没有明文引导 stub、没有可解压的压缩流、入口点直接指向密文区。
所以「破甲 → 逆向 → 出无激活码版本」这条链在**这一个文件**上是断的——
静态拿不到明文程序，动态也起不来（CPU 跳到入口点只会执行到垃圾字节）。
要出成品，必须先拿到「能跑的那个东西」：卖家的启动器 / 可运行安装包 / 或者在有 Windows 的机器上抓一次运行时内存转储。

|---|---|---|---|---|---|
| `.text` | 0x00001000 | 0x00119442 (1.12 MB) | 0 | **0** | ❌ 没有 |
| `.rdata` | 0x0011b000 | 0x01e5fab2 (**30.4 MB**) | 0 | **0** | ❌ 没有 |
| `.data` | 0x01f7b000 | 0x0008aa8a (0.54 MB) | 0 | **0** | ❌ 没有 |
| `.z{+` | 0x02006000 | 0x0097f900 (9.5 MB) | 0 | **0** | ❌ 没有 |
| `.K0[` | 0x02986000 | 0x000007cc (1,996 B) | 0x1000 | 0x1000 | ✅ 熵 4.10（指针表） |
| `.KPx` | 0x02987000 | 0x02b014f0 (**43.0 MB**) | 0x2000 | 0x2b02000 | ✅ 熵 **7.99**（密文） |
| `.rsrc` | 0x05489000 | 0x00027bce | 0x2b04000 | 0x22000 | ✅ 熵 3.38（明文资源） |

三条硬事实：

1. **原程序的 4 个段（.text/.rdata/.data/.z{+）在文件里一个字节都没有**（`SizeOfRawData = 0`）。
   Windows 装载时只会把它们填成 0 —— 也就是说"真正的程序内容"不在这些段里，而在 `.KPx` 里。
2. `.KPx` 是 43 MB、熵 7.99 的**密文**（43 个 1 MB 块里 84% 熵 > 7.9）。
3. 入口点 `AddressOfEntryPoint = 0x2AF1DD3` 落在 `.KPx` 内部（段内偏移 `0x16ADD3`，文件偏移 `0x16CDD3`）。

## 3. 入口点处不是代码（决定性证据）

用 capstone 从 EP 线性反汇编 4 KB：

```
0x56cdd3: e8e1b06402   call 0x2bb7eb9
0x56cdd8: 5e           pop esi
0x56cdd9: 56           push esi
0x56cdda: 1ba070960c55 sbb esp, [eax+0x550c9670]
0x56cde0: 7398         jae 0x56cd7a
0x56cde2: fa           cli
0x56cde3: 06           push es
0x56cde4: 15dbb273d8   adc eax, 0xd873b2db
0x56cde9: b2b6         mov dl, 0xb6
0x56cdeb: fd           std
```

**连续可解码字节只占 0.61%**（10 条指令后彻底崩），指令语义是随机噪声。
对比一下：任何真实编译产物（哪怕再小的壳 stub）在这个指标上都是 **30%~100%**。

### 3.1 但壳的 stub 确实存在 —— 在 `.KPx` 的**尾部**（关键补充）

对全文件做 4 KB 滑窗，找"100% 可解码 + 指令构成像虚拟机解释器"的窗口
（判据：`not/neg/rol/ror/bts/btc/xor/shl` 这类位运算占 >25%，且 `mov/xor/lea` 主导）：

```
窗口数：382 个 4 KB（≈1.5 MB 有效代码）
区间：file 0x282C000 ~ 0x2A24000   →  RVA ≈ 0x5191000 ~ 0x53B0000（VA 再加基址 0x400000）
占比：位运算均值 42%
```

抽样反汇编（file `0x2A23000`）：

```asm
mov  ecx, [ebp+4]                      ; 取"虚拟机栈帧"
mov  [esp], edx
xchg [esp+ecx*4-0x31CC0], edx          ; 按滚动索引读写 VM 栈
call 0x2d6b12d                         ; 调度下一个 handler
xor  eax, ebx
not  eax / neg eax / ror dl,0x87 / bts edx,0x9b / btc edx,ecx
```

这是**教科书级的 VM 型保护壳（VMProtect 3 一类）的 handler/mutation 代码**：
每个 4 KB 都 100% 可解码、`mov/xor/lea/not/neg/ror/bts/btc` 占绝对多数、
大量 `[esp+reg*4-imm]` 形式的 VM 栈访问。

→ 所以修正一句：**壳是存在的（虚拟机型），但 PE 头里的入口点没有指向它。**

### 3.2 EP 与 stub 错位 = 这个文件不能直接跑

| | 值 | 说明 |
|---|---|---|
| PE 头声明的 EP | RVA `0x2AF1DD3` | 落在 `.KPx` 密文区（段内 0x16ADD3） |
| 壳 stub 实际所在 | RVA ≈ `0x5191000 ~ 0x53B0000` | `.KPx` 尾部 2 MB 明文代码 |
| 两者偏差 | ≈ 40 MB | 完全不相干的两片区域 |

Windows 装载时只会跳到 `0x2AF1DD3` 那片密文上执行 → 立刻崩。
也就是说：**头部记录的入口被剥离/改写过（或被外层工具重排过）**，
壳代码在文件里，但没有任何东西会把控制流交给它。

## 4. 不是"压缩壳"，是"真加密"

对 `.KPx` 前 8 MB 做了暴力探测：

- `78 01/9c/da/5e`（zlib 各档）候选 2,460 处 → 尝试解压 **0 个成功**
- LZMA（`5D 00 00 ...` 独立格式）候选若干 → **0 个成功**

再对 2 MB 数据做重合指数（IoC）扫描，检查是否存在**重复密钥 XOR**：

```
global IoC = 0.004563      （随机 = 0.003906，英文 = 0.0667）
按步长 1..64、128..4096 分组 IoC 全部 ≈ 0.00456，无任何步长凸起
```

→ 不是单字节/短周期 XOR，是**流密码/分组密码级**的加密（RC4/AES/ChaCha 类）。
没有密钥、没有 stub 的情况下，静态解密不存在可行解。

## 5. 它是"什么"程序（明文部分能看出来的）

明文只留下 `.rsrc` 和导入表，但这些足够定位技术栈：

**导入表**（15 个 DLL，函数名完整残留）

| 证据 | 含义 |
|---|---|
| `MSVFW32.dll / AVIFIL32.dll / MSIMG32.dll / WINSPOOL.DRV` + `OLEAUT32` 序号导入 | 典型的 **Borland / Embarcadero VCL（C++Builder / Delphi）** 运行库指纹 |
| `COMCTL32/ImageList_*`、`USER32/GrayStringA`、`GDI32/StartDocA` | VCL 控件与打印子系统 |
| `ADVAPI32`：`RegCreateKeyExA / RegQueryValueA / RegSetValueExA / RegOpenKeyExA` | 授权信息落在注册表（卡密/机器码常见做法） |
| `WS2_32`：12 个序号导入（socket/connect/send/recv 族） | **有联网校验**（卡密服务器验证） |
| `KERNEL32`：`CreateProcessA / WinExec / GetVolumeInformationA / GetSystemTime / FindResourceA` | 会拉起子进程、读卷序列号（机器码来源之一） |

**资源段**（明文）

- 清单：`<assemblyIdentity name="E.App" processorArchitecture="x86" version="5.2.0.0">`（VCL 程序默认清单名）
- 对话框/图标/光标：`IEXT_IDR_WAVE1`、`IEXT2_IDC_HORZLINEMOVECURSOR`、`IDB_STATEIMAGES` 等（C++Builder 标准资源名）
- **没有 VERSIONINFO**（被剥掉了，防止一眼看出产品名/版本）

**`.K0[` 段（1,996 字节 = 499 个 dword）**

- 熵 4.10，值域全部落在镜像地址空间内（`0x02xxxxxx ~ 0x54xxxxxx`），21 个 0 分隔
- 形如 `048252b4 / 029c849e / 050ef29c / 02a43146 ...`
- 判读：这是壳自己的**重定位/区块索引表**（记录"哪块密文解密后放到哪个地址"），
  它本身不含解密逻辑，只是被壳读取的**数据**。

**入口之外的辅助证据**：本地没有 `.reloc`（固定基址 0x400000）、没有 `.tls`、没有调试目录，
Checksum = 0 —— 都是"人工重写过的 PE 头"的特征，不是编译器原样输出。

## 7. 卡点到底在哪

正常加壳程序：

```
[PE 头] → [明文 stub，EP 就指在这] → 解密/解压 → 填 .text → jmp OEP → 原程序跑起来
```

这个文件：

```
[PE 头，EP=0x2AF1DD3 → 密文]     ← 断点在这
[.KPx 密文 40 MB]
[.KPx 尾部 1.5 MB：VM 壳 stub（明文，但没人会跳到它）]
```

三个可能性，按概率排：

1. **它本来就是"载荷"**：卖家另配一个 loader（登录器）负责解密并把控制流交给这段 stub，
   卡密校验也在 loader 里 —— 这类卡密工具的常见架构。
2. **它被外层工具二次处理过**：外层只重写了 PE 头/入口，壳体没跟过来（分发/分享环节常见）。
3. **它就是完整可跑的程序，只是入口点被刻意改坏**（反拷贝的小手段）——
   如果是这种，把 EP 改回 `0x5191000` 附近就能起，5 分钟即可验证。

不管是哪一种，**可爆破的点都不在这 43 MB 密文里**：
要么在 loader 里，要么在把 EP 改回来之后的运行时内存里。

## 8. 继续拿到成品的三条路（按性价比排序）

### 路线 0（5 分钟，先试这个）—— 把 EP 改回壳 stub

```bash
python3 tools/set_ep.py samples/HWIDMaster-0902.exe 0x5191000 --out HWIDMaster_epfix.exe
```

在 Windows 上双击 `HWIDMaster_epfix.exe`：

- **起界面了** → 太好了：这就是"入口点被改坏"的样本，
  接着走 `docs/02` 的第 3 步（脱壳）→ 第 5 步（找门）→ 第 6 步（打补丁）
- 还是秒退 → 把 EP 按 `0x1000` 步进往上试几档（`0x5192000 / 0x5193000 / 0x51A0000 …`），
  仍不行就说明是上文可能性 1 或 2，转路线 A/C

### 路线 A（最快，强烈建议）—— 给"能弹出激活窗口的那个版本"

只要拿到**双击能起界面**的同款版本（哪怕是试用版/损坏功能的版本），
剩余工作全部是常规活：

1. `tools/pe_triage.py` 判定壳型（如果它也是壳，就走路线 B 的运行时脱壳）
2. 脱壳 → `tools/delphi_gate.py` 自动定位"激活码/卡密"判定门
3. 打补丁（跳过判定 / 让校验函数恒返回真）→ 出成品 + 补丁日志

### 路线 B —— 在 Windows 上让它跑一次，抓内存转储给我

如果这文件在 Windows 上其实能跑（可能性低，但必须先验证一次）：

1. 双击看进程是否秒退（秒退 = 印证第 3 节的结论）
2. 若能起界面：`procdump64.exe -ma HWIDMaster-0902.exe hwid.dmp`
   （或 Process Hacker → 右键进程 → Create dump file）
3. 把 `hwid.dmp` 丢回来 → `tools/dump2exe.py` 重建 PE → `tools/delphi_gate.py` 找门 → 打补丁

### 路线 C —— 从卖家/资源站拿完整包

问清三件事：有没有**启动器/登录器**、是不是**一机一码按机器下发密钥**、
有没有**离线版**。拿到 loader 后，分析与爆破对象换成 loader。
